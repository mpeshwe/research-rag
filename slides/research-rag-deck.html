Hi everyone. Today I want to walk you through Research RAG — a project I built to fix the single biggest weakness in most retrieval-augmented generation systems: they don't know when they've retrieved the wrong thing. The headline idea is a RAG pipeline that grades its own work and corrects course before it answers. I'll cover why naive RAG fails, the five-stage architecture, and the LangGraph feedback loop that ties it together. Built on LangChain, LangGraph, ChromaDB, GPT-4o-mini, and Tavily.
The Problem

Naive RAG answers confidently wrong

The standard recipe everyone ships:

  • Embed the query
  • Grab nearest chunks
  • Generate an answer

It breaks the moment retrieval returns something irrelevant — the model answers anyway, with full confidence.

Three failure modes

  • Vocabulary mismatch — one phrasing ≠ all phrasings of an idea
  • No structure — "papers under 50k words" can't be a similarity search
  • No fallback — if the corpus lacks the answer, it hallucinates

The magic isn't a bigger model — it's giving the system a way to know when it's wrong.

Let's start with the pain. The standard RAG recipe is embed, retrieve nearest neighbors, generate. The problem is it has no quality gate. If the vector search returns something off-topic, the model still answers — fluently and confidently. Three things break it: vocabulary mismatch, where the user phrases a concept differently than the corpus; structured constraints, like "papers under fifty thousand words," which similarity search simply can't express; and the missing-knowledge case, where the answer isn't in the corpus at all and the model just makes something up. The thesis of this whole project is in that last line: the win isn't a bigger model, it's giving the system a way to know when it's wrong.

Overview

What is Research RAG?

A modular RAG system that intelligently searches and retrieves arXiv research papers using advanced query techniques + a corrective feedback loop.

Multi-angle queries

Generates 5 semantic variants + RAG Fusion, HyDE, Step-Back & Decomposition.

Structured filtering

LLM turns plain English into metadata filters: year, authors, word count.

Self-correction

Grades its own retrievals; rewrites + web-searches when they fall short.

5 stage pipeline  ·  6 RAG strategies  ·  1 LangGraph feedback loop
So what is Research RAG? At its core it's a modular system for searching academic papers from arXiv. Three capabilities set it apart. First, it attacks every question from multiple angles — five query variants by default, plus a toolbox of strategies like RAG Fusion, HyDE, Step-Back, and Decomposition. Second, it lets the LLM build structured metadata filters from plain English, so it can filter by year, authors, or word count. Third, and most importantly, it's self-correcting: it grades its own retrievals and, when they fall short, rewrites the query and reaches out to web search. Five stages, six retrieval strategies, one feedback loop. Let's walk the stages.

Here's the whole system on one slide. A question enters at the top. Stage one is ingestion and indexing — done ahead of time. Stage two translates the question into multiple queries. If any are irrelevant, we branch: rewrite the query, run a web search through Tavily, and only then generate. STAGE 1

Ingestion & Indexing

  • Download papers from arXiv across 6 categories
    cs.LG · stat.ML · cs.AI · cs.CL · cs.RO · cs.CR
  • Extract full text + metadata via PyMuPDF
  • Summarize each paper with GPT-4o-mini
  • Index summaries into ChromaDB
  • Cache docs + summaries to disk (pickle)

Why cache?

Embedding + summarizing every paper is the most expensive step. documents_cache.pkl and summaries.pkl mean you pay the OpenAI cost once — subsequent runs load instantly.

Files: docDownload.py, indexing.py

Stage one is the offline groundwork. We download papers from arXiv across six categories spanning machine learning, AI, NLP, robotics, and crypto. PyMuPDF extracts the full text and metadata. Then — and this is a design choice I'll expand on next — we summarize each paper with GPT-4o-mini and index those summaries in ChromaDB. The expensive part is embedding and summarizing, so we cache everything to disk with pickle. The first run pays the OpenAI cost once; every run after that loads in seconds. This is the difference between a demo you dread re-running and one you iterate on freely.

STAGE 1 · DEEP DIVE

Summary-based indexing (MultiVectorRetriever)

Embed something small & clean — return the full thing.

%%{init: {'theme':'dark','themeVariables':{'fontSize':'16px','lineColor':'#4ea1ff','primaryTextColor':'#e6eef7'}}}%% flowchart LR P[Full Paper] --> SUM[LLM Summary] SUM -->|embed| VEC[("`Chroma: summary vectors`")] P -->|store raw| BS[("`ByteStore: full documents`")] Qr[Query] -->|search clean vectors| VEC VEC -->|matched id| BS BS --> OUT[Return FULL paper to the LLM] style VEC fill:#0d2c47,stroke:#4ea1ff style BS fill:#2b1340,stroke:#b95cff style OUT fill:#0c3326,stroke:#27e0a0

Best of both worlds: precise retrieval on tight summaries, rich context from full documents.

Here's that indexing choice in detail — it uses LangChain's MultiVectorRetriever pattern. Instead of embedding raw paper text, we embed a concise LLM-generated summary of each paper. Summaries are short, dense, and noise-free, so similarity search over them is far more precise. But we don't want to answer from a summary — so separately we keep the full document in a byte store. At query time we search the clean summary vectors, get a match ID, and use that ID to pull back the complete paper for the model. Precise retrieval, rich context — you don't have to trade one for the other.

STAGE 2

Query Translation

One query is limiting. Generate 5 semantically diverse variants to beat the vocabulary-mismatch problem — plus a toolbox of strategies for harder questions.

TechniqueBest for
Multi-Query defaultGeneral use — 5 angles on one question
RAG Fusion (RRF)Re-ranking results across multiple queries
DecompositionComplex, multi-part questions
Step-BackAbstract / conceptual questions
HyDESparse or highly technical corpora

File: QueryTranslation.py

Stage two solves vocabulary mismatch. A single query is one point in embedding space — if the user's phrasing doesn't match the corpus, you miss good documents. So by default we generate five semantically diverse rewordings of the question and retrieve for all of them. Beyond that, the codebase ships five interchangeable strategies. RAG Fusion re-ranks across queries using reciprocal rank fusion. Decomposition splits complex multi-part questions into sub-questions. Step-Back asks a more abstract version first, great for conceptual questions. And HyDE generates a hypothetical answer document to search with, which shines on sparse technical corpora. You pick the tool that fits the question.

STAGE 3

Query Construction & Retrieval

The SelfQueryRetriever reads plain English and builds structured metadata filters automatically.

  • Filter by title, authors, published_year, word_count
  • enable_limit=True → LLM decides how many docs to pull
  • fix_invalid=True → auto-recovers from bad filters
  • Deduplicate by title across all 5 queries

"…under 50,000 words"

A pure similarity search can't honor that. The self-query layer translates it into a real filter:

word_count < 50000

File: QueryConstruction.py

Stage three is where structure comes in. LangChain's SelfQueryRetriever uses the LLM to read the natural-language question and emit a structured filter over metadata — title, authors, published year, word count. The flags matter: enable_limit lets the model decide how many documents to return, and fix_invalid makes it gracefully recover from a malformed filter instead of crashing. The example on the right is the punchline — "papers under fifty thousand words" is impossible for pure similarity search, but trivial once the LLM turns it into word_count less than fifty thousand. Finally we deduplicate by title across all five queries so we don't grade the same paper twice.

STAGE 4 · THE CORE IDEA

Corrective RAG — a LangGraph loop

%%{init: {'theme':'dark','themeVariables':{'fontSize':'16px','lineColor':'#4ea1ff','primaryTextColor':'#e6eef7'}}}%% flowchart LR START([START]) --> R[retrieve] R --> G["`grade_documents binary LLM relevance`"] G --> D{decide_to_generate} D -- all relevant --> GEN[generate] D -- any irrelevant --> TQ[transform_query] TQ --> WSN["`web_search_node Tavily`"] WSN --> GEN GEN --> END([END · Answer]) style D fill:#3a2f0a,stroke:#ffce5a style WSN fill:#0d2c47,stroke:#4ea1ff style GEN fill:#0c3326,stroke:#27e0a0

Every retrieved document gets a yes/no relevance grade. If anything's off, the graph rewrites the query and falls back to web search before generating. A real feedback loop — not a one-shot pipeline.

Files: CRAG.py, graphCrag.py

This is the heart of the project — Corrective RAG, built as a LangGraph state machine. Walk the graph: retrieve injects our candidate documents into state. Grade_documents asks the LLM for a binary yes-or-no relevance judgment on each one. Then decide_to_generate is a conditional edge — the branch point. If every document is relevant, we go straight to generate. If any document is irrelevant, we don't just shrug and answer anyway — we transform the query into a better web-search phrasing, hit Tavily for fresh results, and feed those into generation. That's the loop that lets the system recover from bad retrieval. Modeling this as a graph rather than a linear chain is what makes the conditional logic clean and, with LangSmith, fully observable.

STAGE 5

Answer Generation

  • Final docs + question → rlm/rag-prompt from LangChain Hub
  • Generated with GPT-4o-mini
  • Streamed node-by-node via app.stream() for real-time feedback
  • Context kept under a token budget (3,500 chars) to control cost

Grounded by design

The answer is built only from documents that passed grading — or from fresh web results when the corpus came up short. Far less room to hallucinate.

Stage five generates the answer. We use the community-standard rlm/rag-prompt from LangChain Hub, run it through GPT-4o-mini, and stream the output node-by-node so the user sees progress in real time. We also cap the context at around thirty-five hundred characters to keep token costs predictable. The important property is on the right: the answer is grounded only in documents that passed grading, or in fresh web results when the corpus came up short. Because nothing ungraded reaches the prompt, there's far less room to hallucinate.

Tech stack

Quick tour of the stack. LangChain and LangGraph handle orchestration and the state machine. GPT-4o-mini does the heavy lifting — generation, summarization, grading, and query rewriting — paired with OpenAI embeddings. Storage is ChromaDB for vectors, an in-memory byte store for full documents, and pickle for the disk cache. Knowledge comes from the arXiv API and, as a fallback, Tavily web search. And for tooling, PyMuPDF parses the PDFs while LangSmith traces every LLM call end to end, which was invaluable for debugging the grading loop.

End to End

A query, start to finish

"What are the most influential papers on reinforcement learning with words less than 50,000?"

  • 1. Generate 5 variants on "influential RL papers"
  • 2. Self-query adds filter word_count < 50000
  • 3. Retrieve top matches per query, dedup by title
  • 4. CRAG grades each doc for RL relevance
  • 5. If gaps → rewrite + Tavily web search
  • 6. Stream a grounded, cited answer
Let's make it concrete with one query: "the most influential papers on reinforcement learning with words less than fifty thousand." Watch every stage fire. Stage two generates five variants around "influential RL papers." Stage three's self-query attaches the word_count filter — the part naive RAG can't do. We retrieve per query and deduplicate. Stage four grades each result for actual RL relevance. If there are gaps, it rewrites and pulls from the web. And finally we stream a grounded answer. One sentence from the user exercises the entire pipeline.

What I Learned

Takeaways

Retrieval > prompts

A grading + correction loop did more for answer quality than any prompt tweak.

Index summaries

Searching tight summaries and returning full docs beats chunking raw PDFs.

Let the LLM filter

Self-query unlocks structured questions similarity search simply can't answer.

Graphs > chains

LangGraph makes conditional, self-correcting flows clean and observable.

Cache aggressively

Pickling docs + summaries turned a costly rebuild into an instant reload.

Always have a fallback

Web search means "not in the corpus" no longer means "hallucinate".

Six things I'm taking away from this build. One: retrieval quality beats prompt engineering — adding the grading-and-correction loop moved the needle more than any prompt I wrote. Two: index summaries, not raw chunks — it improved precision noticeably. Three: let the LLM build filters — self-query unlocked a whole class of structured questions. Four: model complex flows as graphs, not chains — LangGraph kept the conditional logic clean and observable. Five: cache aggressively — it changed how fast I could iterate. And six: always have a fallback — web search means "not in the corpus" stops meaning "make it up."
